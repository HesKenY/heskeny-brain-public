Strategic roadmap
  1. 1

    Distribution: trade-specific entry points

    CHERP solo→company funnel with per-trade variants

    Each trade discipline receives a branded mobile application available at no cost. Individual crews adopt the application standalone; conversion to paid company-wide deployment occurs once a connection request is approved by a foreman.

    Seven trade-named PWAs (Pipe Trades, Electricians, HVAC, Fire Sprinkler, Carpentry, Concrete, Safety, General) on cherp.live, plus a federation-v0 device-code flow that attaches a worker's solo app to a company instance. Single Supabase backend, runtime CHERP_TRADE flag.

  2. 2

    Monetization: company-tier instances

    Per-company isolation with SharePoint integration

    Each customer receives a dedicated CHERP environment with company-level data isolation. Daily logs, photos, and signed JSAs flow into the customer's existing Microsoft 365 SharePoint site, eliminating the need for office staff to adopt new software.

    Tier-A architecture: single Supabase project with RLS isolation per company_id. Wave-1 and Wave-1b SharePoint daily-folder routing in production for Debe Corp, the first paid instance.

  3. 3

    Engineering capacity: autonomous maintenance

    KenOS controller with gated self-modification

    Routine engineering work — feature implementation, bug remediation, schema migrations — is performed by a local AI system, with each change verified against an evidence ledger before merge. Customers benefit from reduced release latency without expansion of engineering headcount.

    KenOS v1.2 dispatches goals to the kenai-fullstack and kenai-wolverine agents. Wolverine carries gated self-write authority over its own controller source. A cross-agent claim verifier validates every claimed change against the filesystem and git history.

  4. 4

    Capability validation: live-response training

    kenai-trainer — Pokémon Crystal completion as a Play→Break→Fix benchmark

    We validate the autonomous engineering capability by tasking a dedicated AI variant with completing a complex video game environment without human intervention. The decision loop required — observe state, attempt action, learn from outcome, refine — is the same loop used to remediate CHERP defects in production. Successful completion is a public, externally-verifiable demonstration that the system is capable of multi-step reasoning under uncertainty.

    kenai-trainer:latest drives mGBA via xdotool, produces lesson seeds (84 banked to date), maintains a separate corpus from the kenai-v5 development corpus per the no-dilution rule. The same loop pattern is reused for CHERP migrations and live remediation.

  5. 5

    Operator visibility: shared real-time access

    President access surface mirrored from operator state

    The President side and the Operator side share a single source of truth. Build progress, deployment health, customer SharePoint surfaces, and recently-shipped work all surface here automatically — no separate status meeting required to know where things stand.

    This panel is regenerated from BRAIN canonical state (project-checklist.json, master.log JSONL, claim-checks evidence) on a cron and pushed to the public mirror. No hand-curated status decks; the data is always the data.

Architecture

System overview

Field crews and office staff interact through the CHERP application. All entries are written to the cloud database and, for enabled customers, mirrored to their existing SharePoint environment. Engineering and remediation are performed by AI agents running on local GPU infrastructure, with every action recorded in a unified evidence ledger.

Static PWA → Supabase (REST + RLS) + Netlify functions → Microsoft Graph (SharePoint). Local KenAI on Ollama via litellm Anthropic-compatible proxy → KenOS v1.2 controller → workspace-jailed tools. BRAIN holds canonical state (master.log JSONL + handoffs + evidence).

Quality assurance

Cross-agent claim verifier

Every modification claimed by an AI agent is automatically validated against the filesystem and version-control history. Claims that reference files which do not exist, or commits which were not made, are flagged and surfaced. This mechanism produces a continuous, evidence-based record of what the system actually delivered.

scripts/brain-agent-claim-checks.py — file-path and commit-SHA token verification across BRAIN, CHERP, and home roots. Per-actor breakdown. Surfaced via the Heskeny-Brain evidence dashboard.
